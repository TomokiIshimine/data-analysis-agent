# 開発規約 — 資産の書き方と保守

`.claude/` 配下のワークフロースキル・サブエージェント定義・How スキルを追加・改修するときに守る、このプロジェクト固有の規約。資産の一覧と役割は `docs/architecture.md`、規約の背景にある判断は `docs/design-decisions.md` を参照。

## 言語と命名

- 本文はすべて日本語で書く。識別子・ファイル名・frontmatter の値は英語のケバブケース。
- 分析ドメインの資産は `analysis-` 接頭辞を付ける（`analysis-executor`、`analysis-run-recording` など）。役割名そのものが一意に伝わる場合は例外とし、`data-ingestion-profiler`（データ取り込み係）、`reproduction-verifier`（再現検証係）、`html-deliverable-design`（分析以外の HTML 成果物にも使う指針）がこれにあたる。
- 他ファイルへの参照パスは、永続ファイル（CLAUDE.md・ドキュメント・スキル・エージェント定義）の本文中ではプロジェクトルートからの相対パスで書く。実行時にメインからサブエージェントへ渡すパスは絶対パスにする。

## サブエージェント定義（`.claude/agents/<name>.md`）

- **frontmatter**: `name`・`description`・`model`・`color`。`description` にはメインが起動判断に使う 1〜2 文の責務と、インスタンス粒度（「1 体」「1 インスタンス = 1 周回」）を書く。
- **本文の構造**: `# 責務` → `## 入力` → `## 出力` → `# 判断基準` → （必要なら `# 作業手順（このエージェント固有の How）`）→ `# 使用するスキル` の順。
- **入力**: すべて引数名と 1 行の説明で列挙する。パスは絶対パスで受け取る前提で書く。
- **出力**: 書き出すファイルと、最終メッセージが「成果物の絶対パス 1 行のみ」であることを明記する。
- **判断基準**: 「何をするか」と「なぜそう判断するか」を書く。手順の羅列ではなく到達点と判断の根拠を書く。
- **使用するスキル**: 参照する How スキルを名指しし、どの節を何のために読むかを 1 行添える。使わない場合は「なし」と理由を書く。

### サブエージェントの共通契約

すべてのサブエージェントが守る。個々の定義ファイルに再掲されているのは、各エージェントが独立コンテキストで動くためである。

- `AskUserQuestion` を呼ばない。ユーザーに問うべき論点は推奨値と根拠を固定見出しに列挙するに留め、メインが問う。
- 出力先のパスは引数で受け取る。ファイル名や配置の規約を自分で決めない。
- 正常終了時の最終メッセージは成果物の絶対パス 1 行のみ。要約や説明を付けない。
- 入力の不整合（パス不在、前提の崩れ）を検出したら、編集系ツールを呼ばず、成果物を書かず、絶対パスを返さずに、対象・期待値・実測値を報告して終わる。
- `src/` や `docs/` に書かない。書いてよいのは引数で渡された `tasks/` 配下のパスだけ。
- メインが読む判定値（`SATISFIED` / `CONTINUE`、`REPRODUCED` / `MISMATCH` など）は、成果物内の固定見出しの直下に 1 語で置く。

## How スキル（`.claude/skills/<name>/SKILL.md`）

- **frontmatter**: `name`・`description`。`description` には「何を定めるか」と「どの場面で参照するか」を書く。
- **本文の構造**: `## 適用場面`（利用するサブエージェントと参照する節の対応）→ 規約本文 → `## 本スキルが定めないもの`。
- 2 体以上のサブエージェントが共有する How は、各定義ファイルに書き写さず、必ず How スキル 1 本に集約する。
- プロジェクト固有のドキュメント（`docs/*`、`README.md`）を参照しない。他の How スキルとの間で同じ項目を二重に定めない（担当を分け、境界を `## 本スキルが定めないもの` に書く）。

## ワークフロースキル（`.claude/skills/<name>/SKILL.md`）

- **frontmatter**: `name`・`description`・`argument-hint`・`disable-model-invocation`。重量級ワークフローは `disable-model-invocation: true` にする。
- 必ず持つ節: `## 共通契約への準拠`（メインの作法）、`## 限定 Read 契約（固定見出しテーブル）`、`## 中間生成物の命名規約`、`## 実行手順`、`## 最終報告`、`## 失敗時のリカバリ`。
- 中間生成物の命名規約はワークフロースキルだけが保持する。サブエージェントやドキュメントに写さない。
- 各 Step は「委譲先・引数・期待する戻り値」のテンプレで揃える。

## ドキュメントの更新義務

ドキュメントは資産の地図であり、資産と乖離したら価値を失う。次の変更をしたら同じ作業の中でドキュメントを更新する。

| 変更 | 更新するファイル |
|---|---|
| サブエージェント・How スキルの追加・改名・削除、使用スキルの変更 | `docs/architecture.md`（一覧表と依存マトリクス） |
| ステップ構成やループ制御の変更 | `docs/architecture.md`（7 ステップの概観） |
| 構造的な判断（層・契約・既定値・運用の変更） | `docs/design-decisions.md`（追記。既存項目は消さない） |
| 全エージェント共通の前提の変更 | `CLAUDE.md`（60 行以内を維持） |
| 起動方法や前提条件の変更 | `README.md` |

`CLAUDE.md` には要点とパスだけを置き、本文はドキュメントに置く。

## Git 管理

コミットしないもの（`.gitignore` で除外済み）:

- `tasks/` 全体。ワークフローの作業ディレクトリは揮発系であり、元データの複製を含みうるため、公開リポジトリに載せない。
- `.claude/settings.local.json`。個人環境の権限設定。
- `.DS_Store`。

コミットするものは `.claude/agents/`・`.claude/skills/`・`docs/`・`README.md`・`CLAUDE.md`・`LICENSE`・`.gitignore` に限られる。

## セルフチェックの観点

資産を追加・改修したら、次の 5 観点で見直す。ワークフロー生成時のレビューで用いた観点と同じ。

1. **設計忠実**: 設計書や依頼内容と生成物が一致しているか。引数名・ファイル名・判定語が揃っているか。
2. **規約**: 本書の構造・命名・共通契約に従っているか。
3. **機械可読**: メインが限定 Read する固定見出しと判定語が、決めた位置に決めた形で置かれるか。
4. **プロンプト品質**: 到達点と判断基準を書いているか。冗長・曖昧・多義な記述がないか。
5. **コンテキスト設計**: 同じ情報が 2 箇所に無いか（DRY）。全エージェント共通でない情報が `CLAUDE.md` に入っていないか（最小コンテキスト）。資産からドキュメントへの参照や、サブエージェント間の暗黙の依存が生まれていないか（疎結合）。
