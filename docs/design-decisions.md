# 設計判断の記録

`/data-analysis` ワークフローとリポジトリ運用に関する構造的な判断を、決定・根拠・捨てた代替案・影響範囲の 4 項目で記録する。手順や引数はここに書かない（`.claude/skills/data-analysis/SKILL.md` が正）。How の本文も書かない（各 How スキルが正）。

判断 1〜10 は 2026-09-10 のワークフロー設計時に確定したもので、出典はワークフロー生成時の設計書（`tasks/2026-09-10_data-analysis/02_workflow-design.md`。`tasks/` は Git 管理外のため、他環境には存在しない）。本書がその恒久記録である。

## 1. プロジェクト内で自己完結する

- **決定**: ワークフロースキル・サブエージェント 9 体・How スキル 4 本はすべて `.claude/` 配下に置き、外部プラグイン（`claude-code-workflow-kit` 等）のサブエージェント・スキルを一切参照しない。
- **根拠**: クローンした別環境にプラグインがある保証がない。「動く条件」をリポジトリ内に閉じる。
- **捨てた代替案**: プラグインの `design-cycle` How スキルと `workflow-init` サブエージェントを流用する。ファイル数は減るが、環境依存が生まれる。
- **影響範囲**: `analysis-design-cycle` と `analysis-workdir-initializer` はプラグイン側の同等資産と概念的に重複する。リポジトリ境界をまたぐ重複は DRY 違反とみなさず、プロジェクト内の定義を単独の正とし、プラグイン側との同期は試みない。プロジェクト内部では DRY を厳守する。

## 2. データ取り込みとプロファイリングを要件定義の前に置く

- **決定**: Step 2 でデータソースを解決し台帳とプロファイルを作ってから、Step 3 で要件シートを起草する。
- **根拠**: 実データの列・型・件数・欠損を知らずに書いた要件は判定可能な完了条件にならず、承認ゲートでユーザーが判断する材料も欠ける。「欠損の多い列を対象にしない」といった判断は実データを見ないと下せない。
- **捨てた代替案**: 要件定義の直後にプロファイリングする。要件を書き直す手戻りが承認ゲートを 2 周させる。
- **影響範囲**: データソースが起動引数に無い場合、profiler は推測せず `UNRESOLVED` と候補を記録し、承認ゲートで確定させてから再解決する。

## 3. 立案・実行・評価・再現検証を別エージェントに分ける

- **決定**: 分析ループは `analysis-planner` → `analysis-executor` → `analysis-evaluator` の 3 体、再現検証は `reproduction-verifier` が担う。
- **根拠**: 立案者に自分の結果を採点させない独立性を確保する。再現検証はレポートだけを情報源とする第三者役であり、他の中間生成物を見せない。
- **捨てた代替案**: 1 体が立案から評価まで通す。コンテキストは節約できるが、自己採点になる。
- **影響範囲**: 周回ごとにインスタンスを新規起動する（1 インスタンス = 1 周回）。`data-ingestion-profiler` も同じ理由で独立した 1 体にした（要件定義の前に完了する必要があり、周回に依存しない一度きりの責務のため）。

## 4. 分析要件の唯一の情報源を HTML 1 本にする

- **決定**: `02_analysis-requirements.html` を要件の唯一の情報源とし、Markdown 版を持たない。承認ゲートの要約セクションは `<section id="design-summary">` に固定する。
- **根拠**: ユーザーとのすり合わせは HTML で行うという要求を満たしつつ、Markdown 版との二重管理（revise 時の同期漏れ）を避ける。
- **捨てた代替案**: Markdown を正、HTML を派生ビューにする。承認のたびに 2 ファイルを同期する必要があり脆い。
- **影響範囲**: HTML を書く主体が 2 体（`analysis-requirements-designer`、`analysis-report-stylist`）あるため、デザイン指針を `html-deliverable-design` に集約した。テンプレートは提供しない。

## 5. 元データは既定で複製せず、参照と SHA-256 照合で同一性を担保する

- **決定**: 台帳に絶対パス・SHA-256・サイズ・件数・スキーマ・取得日時・機密区分を記録し、分析実行の直前にハッシュを照合する。複製は「非機密かつ 100 MB 未満のローカルファイル」に限り、再取得で変わりうる非機密ソースは決定的スナップショットを保存し、機密なら保存せず取得条件のみ記録する。機密区分は要件シートの必須項目とし、既定は保守側（掲載しない）。
- **根拠**: 再現性に必要なのは「同じデータであることを検証できること」であり複製そのものではない。機密データを作業ディレクトリに落とすリスクは再現性の利益を上回る。
- **捨てた代替案**: 常にコピーする。大容量・機密データで破綻する。
- **影響範囲**: 台帳の内容はレポートにも転記される。これは DRY 違反ではなく、実体は台帳 1 つ、レポート側は第三者が単体で読むための転記と位置づける。規約は `analysis-data-handling` に集約。

## 6. 実行資産を `runs/` に単体再実行可能な形で残し、前処理は分析ループ内で行う

- **決定**: プロファイリング・分析各周回・再現追試はそれぞれ `runs/<run-id>/` 配下にスクリプト・再実行エントリポイント・環境記録・派生データ・出力・図表を保存する。前処理専用ステップは設けず、周回ごとに `scripts/` と `derived/` に残す。
- **根拠**: ログ中のコード断片では再実行できない。派生データを `run.sh` から再生成可能にすれば「手作業の中間ファイルがないと再現できない」ケースを構造的に防げる。必要な前処理は分析観点ごとに変わり、要件確定前に固定できない。
- **捨てた代替案**: 前処理を独立ステップにする。観点が変わるたびに手戻りする。
- **影響範囲**: 実行ログ中のコード引用と保存済みスクリプトは、実体はスクリプト 1 つ・ログ側は引用と位置づける。規約は `analysis-run-recording` に集約。

## 7. 明示呼び出し専用にする

- **決定**: ワークフロースキルは `disable-model-invocation: true`。ユーザーが `/data-analysis` と打ったときだけ起動する。
- **根拠**: コード実行・多数のファイル生成・複数の承認ゲートを伴う重量級ワークフローであり、会話中の「データ分析」という語での誤発火コストが利便性を上回る。
- **捨てた代替案**: 自動呼び出しを許可する。「このデータを分析して」で起動する利便性はあるが、軽い集計依頼にまで 7 ステップが走る。
- **影響範囲**: 単発の集計やグラフ 1 枚には使わない。

## 8. 命名規約を知るのは SKILL.md だけにする

- **決定**: 中間生成物のパスはメインが組み立て、サブエージェントには絶対パスを引数で渡す。サブエージェントは命名規約を持たない。
- **根拠**: 疎結合。サブエージェントを個別に変更・再利用でき、命名変更の影響が 1 ファイルに閉じる。
- **捨てた代替案**: 各サブエージェントが規約を知って自分でパスを組む。命名変更が 9 ファイルに波及する。
- **影響範囲**: ドキュメント（`docs/architecture.md` 含む）にも命名テーブルを写さない。

## 9. メインは本文を読まない（限定 Read 契約）

- **決定**: メインは固定見出し（`## 判定`、`<section id="design-summary">` など）だけを読み、ループ制御と承認ゲートに用いる。判定はサブエージェントの戻り値ではなくファイル内の固定見出しから取る。
- **根拠**: 最小コンテキスト原則。長時間ワークフローでメインのコンテキストを枯渇させない。
- **捨てた代替案**: 戻り値に要約を含める。戻り値の形式が崩れやすく、メインが要約を再解釈する余地が生まれる。
- **影響範囲**: メインに渡すべき情報は、サブエージェントが固定見出しに整形する責務を負う。

## 10. 反復上限の既定値は分析 5 周・再現 3 周

- **決定**: N = 5、M = 3 を既定とし、要件シートで上書きできる。
- **根拠**: 5 は要求仕様の明示値。再現検証は原因を探してレポートに反映する修正ループであり、3 周で収束しなければ人間の判断を仰ぐべき。
- **捨てた代替案**: 上限なし。収束しないケースで止まらない。
- **影響範囲**: 上限到達時も中断せず次のステップへ進み、最終報告で上限到達と最終周回のファイルパスを伝える。

## 11. `tasks/` 全体を Git 管理外にする（2026-09-19）

- **決定**: `.gitignore` に `tasks/` を追加し、ワークフローの作業ディレクトリは一切コミットしない。ワークフロー生成時のログ・設計書も対象。
- **根拠**: リポジトリは公開である。ワークフローは条件を満たす元データを `data/raw/` や `data/snapshot/` に複製する設計なので、`tasks/` を push すると分析対象データが公開される。除外を部分的にするより、全体を除外して事故を構造的に防ぐ。
- **捨てた代替案**: `tasks/` はコミット対象のまま `data/raw/`・`data/snapshot/`・`runs/**/derived/` だけを除外する。生成ログの履歴を残せるが、除外漏れのパターンが残る。
- **影響範囲**: 設計判断の恒久記録は本書だけになる。構造的判断をしたら本書に追記する（追記ルールは下記）。

## 12. 完了条件を分析ループ群とレポート工程群に分ける（2026-09-22）

- **決定**: 要件シートの完了条件は ID 接頭辞で 2 群に分ける。`AC-L-<n>` は分析ループの成果物だけで充足を判定できる条件、`AC-R-<n>` はレポート本文・alt テキスト・キャプション・再現手順の記載でしか充足しない条件。`analysis-evaluator` の `## 判定` は `AC-L` 群のみを対象とし、`AC-R` 群は固定見出し `## レポート工程への引き継ぎ事項` に列挙してレポート工程へ渡す。`analysis-report-author` が `AC-R` 群の充足を自己点検して記載する。
- **根拠**: 2026-09-19 の実行で、完了条件に「本文で言及」「alt テキストがある」といった Step 5 でしか満たせない項が混在し、評価係が全項を分析ループの成果物で判定したため構造的に `SATISFIED` に到達できず、5 周の上限まで衛生作業を重ねた。群を分ければ分析ループは分析の実体が揃った時点で終わる。
- **捨てた代替案**: 要件シート内で群を別セクションに分ける。承認ゲートでユーザーが 2 箇所を突き合わせる負担が増え、メインの限定 Read からも内訳が見えにくい。接頭辞なら評価係・レポート係が本文を解釈せずに機械的に群を判別できる。
- **影響範囲**: `analysis-requirements-designer`（群分けして起草し、`design-summary` に内訳を載せる）、`analysis-evaluator`、`analysis-report-author`、SKILL.md の Step 3-3 / 4-4 / 5。判断 10 の既定値 N = 5 は変えない。

## 13. 確定済み周回の `run-dir` は後続周から改変しない（2026-09-22）

- **決定**: 周回が終わった `run-dir` は不変（イミュータブル）とする。上流の `run-dir` に欠陥が見つかった場合は、修復を行う周回の `run-dir` に修復版を置き、その `run-manifest.md` に上流との関係（対象・欠陥・修復内容・上流を保持している旨）を記録する。唯一の例外は秘密値の伏せ字化で、当該 `run-dir` の `run-manifest.md` に事実と日時を記録して行う。スクリプトは周回番号・`run-dir` パスをハードコードせず、`run.sh` が渡す引数・環境変数から受け取る。
- **根拠**: 各周回の実行ログは当該時点の `run-dir` を前提に書かれている。2026-09-19 の実行で第 5 周が第 1〜3 周の `run.sh` を書き換え、記録と実体が時点でずれた。また前周スクリプトの無改変複製で周回呼称の誤りが生成物に残った。
- **捨てた代替案**: 改変を許し、記録先だけを定める。ずれの発生自体は防げない。
- **影響範囲**: 規約は `analysis-run-recording` に集約。`analysis-executor` は既存資産の修復を `Edit` で行い、その事実を実行ログに記録する（修復スクリプトの実行がサンドボックスに拒否されうるため）。

## 14. 骨格ディレクトリと台帳出力先も引数で渡す（2026-09-22、判断 8 の徹底）

- **決定**: `analysis-workdir-initializer` は作成する骨格サブディレクトリの名前を `subdirs` 引数で受け取り、`data-ingestion-profiler` は台帳の出力先を `manifest-output-path` 引数で受け取る。両者とも定義ファイル内に固有のディレクトリ名・ファイル名を持たない。`data-dir` 配下の内部構成（複製・スナップショットの置き場）は `analysis-data-handling` が定める。
- **根拠**: 改修後の観点レビューで、両定義が `data/` / `03_iterations/` / `05_reproduction/` / `runs/` や `data/manifest.md` を保持しており、判断 8「命名規約を知るのは SKILL.md だけ」に反する二重管理になっていることが検出された。
- **捨てた代替案**: 例外として二重保持を明記し、変更時に両方を更新する運用にする。追跡は可能になるが更新漏れの経路は残る。
- **影響範囲**: SKILL.md の Step 1・Step 2・Step 3-4 の引数と `## 中間生成物の命名規約` の表。

## 判断の追記ルール

- 新しい構造的判断（層の追加、契約の変更、既定値の変更、リポジトリ運用の変更）は、番号を増やして本書に追記する。既存の判断を覆す場合は元の項目を消さず、「判断 N を置き換える」と明記して新しい項目を足す。
- 判断が資産の構成を変える場合は `docs/architecture.md` の該当箇所を同時に更新する。
- 判断が全エージェント共通の前提を変える場合のみ `CLAUDE.md` を更新する。
