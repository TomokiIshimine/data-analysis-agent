# analysis-design-cycle — 設計書直書き・承認駆動の 2 モード設計サイクル契約

## 適用場面

入力情報を起点に、設計文書（要件シート・計画書・仕様書等）をユーザー承認のもとで作る流れを採用するワークフローで参照する。本プロジェクトでは `/data-analysis` の Step 3（分析要件定義）が本契約を採用し、設計係は `analysis-requirements-designer` である。

本契約は **設計係**（draft / revise の 2 モードを持つ 1 種類のサブエージェント）と **オーケストレーター**（メイン）の 2 役を規定する。各ワークフローは差分点（ドメイン固有入力・成果物の見出しテンプレ・要約セクションの実体）だけを埋めれば、本契約のとおりに動く。

設計文書と同内容の中間成果物（提案レポート）を別ファイルとして作る工程は **持たない**。draft が成果物本体を直接 Write し、ユーザー確認に必要な観点は成果物先頭の要約セクションに集約する。承認までの修正はすべて同一ファイルへの revise で行い、中間成果物は 1 本に閉じる。

## 設計係の契約

### モード一覧

| mode | 入力（ドメイン固有入力に追加） | 出力 |
|---|---|---|
| `draft` | 成果物の書き出し先絶対パス（必須） | 成果物本体を Write |
| `revise` | 修正対象の絶対パス（必須） ／ `modification-request` | 同一ファイルを Edit |

出力先パスの引数名（`design-doc-path` / `requirements-path` 等）とドメイン固有入力の名前・意味は、各ワークフローが決める。

### 成果物の構造（draft が Write する内容）

draft は指定された絶対パスに成果物本体を直接 Write する。構造は次の 2 部で構成する。

- **要約セクション** — 成果物の **先頭** に置く。メインが限定 Read してユーザーへの確認観点提示に用いる短い要約。
  - 設計の核となる選択（確認観点）を箇条書きで列挙し、各項目に **推奨値と根拠** を 1 行ずつ添える。
  - revise を経た版では、冒頭に **「前回からの主な変更点」** を併記する（初回 draft では不要）。
  - 要約セクションの実体（Markdown なら `## 設計サマリ`、HTML なら `<section id="design-summary">` 等）は各ワークフローが固定的に定める。実体が何であれ、位置は先頭、役割は「限定 Read の対象」で共通とする。
- **本文** — 各設計係が固有差分として規定する見出しテンプレに沿って、推奨値で埋めた成果物本体を展開する。後続工程はこの本文を根拠として動く。

要約セクションは本文の要約であり、**本文と矛盾してはならない**。件数・番号・上限値などの数値は、要約セクションと本文の全箇所で一致させる。

### revise の責務

対象ファイルを `modification-request` の意図に従って Edit する。`modification-request` は複数論点を含む自由記述でよい。

- 本文の修正と要約セクションの更新を **同一の revise 内で同期** させる（サマリだけ・本文だけの片側修正を残さない）。
- 要約セクションの冒頭に「前回からの主な変更点」を記載（既にあれば置き換え）し、メインが再提示する確認観点に差分が現れるようにする。
- Edit 対象のセクション境界（どの見出しを触ってよいか）は各設計係が固有差分として規定する。

### 設計係が AskUserQuestion を呼ばないこと

すべてのユーザー対話はメインが担う。設計係は `AskUserQuestion` を呼ばず、そのスキーマをロードする手順も持たない。成果物に「ユーザーに問うべき論点」が残る場合でも、設計係は **問わずに推奨値で埋める**。推奨値であることと根拠は要約セクションで明示する。判断材料が不足する論点は、保守側（後戻りコストの小さい側）を推奨値にする。

### 前提が崩れた場合の中断

出力先パスが渡されない、`revise` で対象ファイルが存在しない、入力レポート間で値が矛盾している、といった前提の破綻を検出した場合は、**`Edit` を一切行わず**、不整合内容を列挙して終了する。自動補正・推測による補完をしない。

### 設計係が決めること（ワークフロー固有差分）

- (a) ドメイン固有入力の名前と意味
- (b) 要約セクションに列挙する確認観点の項目とその粒度
- (c) 成果物本文の見出しテンプレ（推奨値の並べ方を含む）
- (d) 要約セクションの実体（Markdown 見出しか HTML セクションか、その識別子）
- (e) revise で許容するセクション境界

## オーケストレーター（メイン）の契約

### 承認ゲートの手順

設計係が `mode: "draft"` で Write（または `mode: "revise"` で Edit）した成果物に対し、メインは以下の手順でユーザー承認を取得する。

1. **限定 Read**: 成果物の要約セクション（および各ワークフローが固定見出しテーブルで追加指定した箇所）のみ Read する。**本文全読は禁止**。
2. **確認観点のメッセージ提示**: 限定 Read した要約セクションの内容（確認観点・推奨値・根拠。revise 後は「前回からの主な変更点」を含む）を、ユーザーへのメッセージとして提示する。
3. **`AskUserQuestion` を 1 通発火**:
   - 質問文に成果物の **絶対パス** を必ず含め、ユーザーが実ファイルを開いてレビューできる状態にする。
   - `options`: `[{label: "承認", description: <承認時の挙動>}, {label: "修正要望あり", description: <修正要望時の挙動>}]`
4. 「承認」が選ばれた場合: 成果物を確定とし、後続ステップへ進む。
5. 「修正要望あり」が選ばれた場合:
   - 続けて `AskUserQuestion`（**自由記述スロット 1 件**）で `modification-request` を取得する。質問文に「複数論点をまとめて記述してよい」旨を明示する。
   - 設計係を `mode: "revise"` で再起動する。引数は、対象ファイルの絶対パス・取得した `modification-request`・draft で使ったドメイン固有入力一式。
   - 戻り値（同じ絶対パス）を保持して **手順 1 に戻る**。
6. **反復上限なし**（ユーザーが承認するまで継続）。

### 承認ゲートを設置する位置

承認ゲートは **draft 直後の 1 箇所** に置く。中間成果物が 1 本のため、「提案の承認 → 適用の承認」といった 2 段ゲートは存在しない。承認までの反復（revise → 再提示）はすべてこの 1 箇所のゲート内で完結する。

### 承認なしの自動進行をしない

「修正要望あり」を選ばれた状態で後続ステップに進まない。また、要約セクションを読んだメインが自ら本文を書き換えて承認を代行しない。成果物への書き込みは設計係の責務である。

## 本スキルが定めないもの

- 成果物の具体的な見出し構成・項目（各設計係の責務）
- HTML 成果物の見た目・タイポグラフィ・配色（`html-deliverable-design` の責務）
- `AskUserQuestion` 1 通の質問本文・選択肢の文面の練り方（各ワークフローの責務）
- ワークフローの構成（ステップ数・並列直列・承認ゲート以外の反復制御）
