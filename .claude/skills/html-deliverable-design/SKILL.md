# html-deliverable-design — HTML 成果物のデザイン指針

## 適用場面

本プロジェクトが出力する HTML 成果物を書くときに参照する。想定する成果物は 2 種類。

- **判断のために読む文書**（分析要件シート）— ユーザーが承認 / 修正要望を判断するために読む。
- **結果を確認する文書**（清書レポート）— 分析結果と再現手順を第三者が確認・追試するために読む。

**固定テンプレートは提供しない。** 内容に応じて構成は毎回変わる前提で、以下の指針を満たす形を都度組み立てる。テンプレートの使い回しは、内容と構成のずれを生むため行わない。

## 1. 単一ファイルで完結させる

- CSS・スクリプト・フォント指定・画像を含め、外部ホストへのネットワーク依存を持たない。CSS は `<style>` にインライン、画像は data URI として埋め込む。
- 外部 CDN・Web フォント・アイコンフォントを参照しない。オフラインで開いても、他人に 1 ファイル送っても、同じ見た目で読めることを合格条件とする。
- フォントはシステムフォントスタックで指定する（例: 日本語を含む本文用に、汎用 sans-serif へフォールバックする複数指定）。
- スクリプトは必須ではない。使うのは折りたたみ・目次のスクロール追従・コードのコピーなど、読み下しを助ける範囲に限る。スクリプトが無効でも本文がすべて読めること。

## 2. 情報の優先順位づけと見出し階層

- **最初に見せるもの**: その文書を読む人が最初に必要とする判断材料。要件シートなら確認観点の要約、清書レポートなら結論と再現手順の入口。長い前置きを先頭に置かない。
- **折りたたむもの**: 分量が多く、必要な人だけが開けばよいもの（詳細な統計表、長いコード全文、試行の経緯）。`<details>` / `<summary>` を使い、`<summary>` には中身が推測できる具体的な文言を書く（「詳細」ではなく「第 3 周の実行ログ（stdout 全文）」）。
- 折りたたみの中に、読者が見落とすと判断を誤る情報（機密区分・上限到達・不一致の事実）を入れない。
- 見出しは `<h1>` を 1 つだけ置き、以降は階層を飛ばさずに `<h2>` → `<h3>` と下る。見た目の大きさのために見出しレベルを選ばない（大きさは CSS で調整する）。
- 文書が長い場合は先頭に目次を置き、各見出しの `id` へリンクする。

## 3. タイポグラフィ・余白・行長

- 本文の行長は 1 行あたり全角 40 字前後（`max-width` で `70ch` 程度）に収める。ウィンドウ幅いっぱいに本文を流さない。
- 本文の行間は 1.7〜1.9 程度を確保する。日本語の混在する文章は、欧文だけの想定より広めの行間が読みやすい。
- 本文サイズは 16px 相当を下限とする。フォントサイズの種類は 4〜5 段階に抑える。
- 段落・見出し・図表のあいだの余白で情報のまとまりを表現する。見出しの直前の余白は直後より広く取る（見出しが後続の内容に属して見えるようにする）。
- **読み下しを損なう装飾を使わない**: 影付き文字、装飾フォント、背景画像の上の本文、意味のないアイコン、過剰なアニメーション、正当性のない中央揃えの長文。装飾は情報の区別に必要な範囲だけ。

## 4. 配色

- **ライト／ダーク双方で破綻しないこと**。色は CSS カスタムプロパティとして `:root` に定義し、`@media (prefers-color-scheme: dark)` で値だけを差し替える。個々の要素に色を直書きしない。
- 背景色と文字色は必ず両方を明示する。片方だけ指定すると、閲覧環境の既定色と組み合わさって読めなくなる。
- **色だけに意味を担わせない**。「赤 = 不一致」のような区別は、色に加えてラベル文言・記号・枠線のいずれかを併用する。色覚特性や白黒印刷でも情報が失われないこと。
- 使う色は、本文色・背景色・弱い文字色・境界線色・強調色 1〜2 色程度に絞る。判定や状態の色分けは、意味の数だけ増やさず「注意」「危険」の 2 段階程度に集約する。

## 5. 表・コードブロック・図表の提示規約

**表**

- 表は必ず `overflow-x: auto` のコンテナに入れ、横スクロールを表の内側に閉じ込める。ページ本体が横スクロールしてはならない。
- ヘッダ行は `<th>` を使い、行数が多い表ではヘッダを固定（`position: sticky`）する。
- 数値列は右揃え、桁区切りを入れ、単位を列見出しに書く（セルごとに繰り返さない）。

**コードブロック**

- コードは `<pre><code>` に入れ、等幅フォント・行の折り返しなし・横スクロールをブロック内に閉じ込める。
- **コピーしやすさを最優先する**。行番号・プロンプト記号（`$`）・装飾記号をコード本文に混ぜない（混ぜると選択してコピーしたときに壊れる）。行番号を出す場合は選択対象に含まれない方法を使う。
- コードの直前に「何をするコードか」「どこに保存されているファイルか（相対パス）」を 1 行で書く。
- 長いコードは折りたたんでよいが、`<summary>` にファイル名と役割を書く。

**図表**

- 図表は data URI で埋め込み、外部ファイル参照に依存させない。
- 図表と、その説明文・該当する本文の記述を **近接** させる。文章の末尾にまとめて図を並べない。
- すべての図に `alt` を書く。`alt` には「何のグラフか」ではなく「そのグラフから読み取れること」を書く（「売上の折れ線グラフ」ではなく「売上は 4 月から 8 月にかけて単調増加し、9 月に約 2 割減少した」）。
- 図のキャプションは `<figure>` / `<figcaption>` で構造化する。

## 6. アクセシビリティの下限

- 本文と背景のコントラスト比は 4.5:1 以上、大きな文字（18pt 相当以上）は 3:1 以上を確保する。弱い文字色（補足・キャプション）もこの下限を下回らせない。
- 見出し・リスト・表は、見た目だけで作らず対応する要素（`<h2>` / `<ul>` / `<table>`）で構造化する。スクリーンリーダーと目次生成の両方がこれに依存する。
- リンクテキストは行き先が分かる文言にする（「こちら」を単独で使わない）。
- `<html lang="ja">` を指定する。
- ズーム 200% でも本文が横スクロールなしで読めること（相対単位でレイアウトする）。
- フォーカス可能な要素のフォーカスリングを消さない。

## 7. 文書の種類による強調対象の違い

| 観点 | 判断のために読む文書（要件シート） | 結果を確認する文書（清書レポート） |
|---|---|---|
| 最初に見せるもの | 確認観点・推奨値・根拠の要約 | 結論と、データ入手を含む再現手順の入口 |
| 強調する対象 | 推奨値であること、未確定の論点、判断を要する分岐 | 数値の正確さ、図表と本文の対応、手順の実行順序 |
| 折りたたむ対象 | 背景説明、代替案の詳細 | 長いコード全文、試行の経緯、詳細な統計表 |
| 避けること | 推奨と確定の区別が付かない書き方 | 要約による情報の欠落、コードの整形による改変 |

## 本スキルが定めないもの

- 具体的な HTML テンプレート、コンポーネントライブラリ、ブランド固有の色指定。
- 成果物の見出し構成・掲載項目（各サブエージェントの責務）。
- 機密区分による掲載可否の判断基準（`analysis-data-handling` の責務）。本スキルは「載せると決まったものをどう見せるか」だけを扱う。
